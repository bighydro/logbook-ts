# Changelog

All notable changes to logbook-ts. The format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/);
the versions are this implementation's, and the spec it follows is named in each entry.

## Unreleased

### Changed
- Agreement with the reference at its **main of 22 October 2026** (bighydro/logbook 6ee01c2, twenty PRs past a86787c): `REFERENCE` moves there. Every vendored expected file was captured again from it and none moved; `tests/fixtures/demo-seed1` and `demo-sample` are made again by `logbook demo` there (its #338 marks a demo in `logbook.json`, its #348 writes a policy file with the MCP door at tier 1 and nothing else; demo-sample also takes up `format` 0.3, `import.json` and `handles`, which earlier catch-ups left; the month files and heads are unchanged). The README's *Coverage at 6ee01c2* table says what is implemented, verified only or not implemented; SPEC-QUESTIONS 119–125.
  - **draft/v1 amendment 2** (its #358): `readDraft` reads a `link` proposal (`{kind: link, entity, text, evidence, note?}`) under `links`, numbered by its place among all the proposals, its evidence read on the unit; an event's and a link's `supported` and `why`; each segment's `part` and an idea's `entity` from `extra`; `evening`, `read_until`, `marked`, `dropped`, `dropped_links`, `dropped_segments`; and the reference's sentences for a malformed proposal, for `extra` that is not an object and for an evening draft. An event may leave `place` out, its instants compared to the last digit, and a `kind` of blanks is malformed (SPEC-QUESTIONS 117, answered in part). `PROPOSAL_KINDS` is `event, link`, so a writer may write a link. `show`'s draft row counts `· N proposed events · N proposed links`, as the reference's does (it never printed the count here). `DraftLink` in the library. Two shapes of the library change for a caller that builds them: `DraftSegment` gains a required `part` (and an optional `entity`), `DraftProposal` a required `supported` and `why`; `DraftRead` gains `links`, `evening`, `read_until`, `marked`, `dropped`, `dropped_links` and `dropped_segments`. `draftProblems` takes a proposal's shape from the reader, so a writer's event may now leave `place` out and name an id of blanks, as the reference's reader takes them (SPEC-QUESTIONS 120, 121).
  - **Who a note says was there** (SPEC §3.2.5 rule 3): `with <Name>` is read as the spec and the reference read it, the names capitalised and joined by `and`, `og` or `&`, a first name matched as a transcript participant's is; before, any person's full name after `with` in the sentence counted, so the `not-with:` and `lives-with:` notes of the reference's #351 named the person they exclude. 81 notes in `tests/with-cases.ts`, held to the reference by `tests/cross-impl.test.ts`.
  - Found and not changed: a stay whose next point lies past the reader's window ends at its last point here and at 24:00 in the reference (SPEC-QUESTIONS 123), the same at a86787c.
- `draft/v1`'s forward compatibility (bighydro/logbook rfcs/0036-draft-v1.md, amendment of 2026-10-19, on its main at a86787c, 2026-10-21): `readDraft` reads a draft's `proposals` and shows the event proposals of their shape, numbered by their place in the array, and counts the proposals of a kind it does not know as `proposals_unknown` without calling the line malformed; a known kind of the wrong shape, and a proposal that is not an object or names no `kind`, are still malformed. Writers stay strict: `draftProblems` refuses a kind it does not know. `DraftProposal` and `PROPOSAL_KINDS` in the library. `REFERENCE` moves from b82a11c (0.7.0) to a86787c, the reference's commit that carries the amendment, nine commits past 0.7.0; the cross-implementation test holds both readers to the same `proposals_unknown` and the same count of proposals shown. SPEC-QUESTIONS 117.
- `trips`, the route's text, as the reference prints it since its #343 (fa41791, one of the nine commits to a86787c): an unnamed stay reads `near <place>, x km` or the nearest airport's city (`Zurich`), its coordinates kept only where nothing names it or where a neighbour on the route would read the same (`routeText`); the JSON keeps the labels. The eight `expected-trips/*.txt` files that moved are re-captured from the reference at a86787c; no JSON and no other vendored file moved. SPEC-QUESTIONS 118.

### Added
- Agreement with the reference at **openlogbook 0.7.0** (bighydro/logbook, tag v0.7.0 at b82a11c, 2026-10-18): `REFERENCE` moves from 7bcf728 to b82a11c, every vendored expected file is re-captured there (only rfc0037-0038-sample's Day and `people` moved), and the conformance samples still verify to L1 `58bfa9e7…` and L2 `0ab4c3e7…`. The README's *Coverage at v0.7.0* table says, per changed document, what is implemented, verified only or not implemented; SPEC-QUESTIONS 108–116.
  - **A line superseded twice** (the reference's #321, its docs/SPEC-QUESTIONS.md of 18 October 2026): a line is superseded while a line of its kind that is not retracted names it, and a superseder superseded in turn still supersedes. `show`'s marks, the Day's flights, `people`'s transcripts and calendar entries and the resolver's names read by it (`isSuperseded`); a retracted tracked flight no longer hides the declared one, and a name whose corrections are all retracted stands again.
  - **Who spoke** (RFC 0038 §3, RFC 0006's amendment of 2026-10-15, the `speaker` ref), under `rfc0038`: `bindVoices` binds a voice by the standing resolution of `<transcript line id>#<label>`; the Day names it (`Middag · Kari Nordmann 10 min · you 30 s · 1 unnamed · recorded with consent: unknown`; `person`, `basis`, `consent` under `speakers`, the owner's voice the record's `owner_id`), counts a bound voice as company at a stay (`with … · 2 unnamed`), and `people` counts the transcript with `spoke_s` and says `N voices not yet named · review speakers` and `and N unnamed`.
  - **RFC 0037's portfolio** (amendment of 2026-10-15), under `rfc0037`: `statusProblems` refuses a `portfolio` that is not text, and one on any kind but an org's, in the reference's words; `status list` prints `· portfolio Fund I` and gives `portfolio` and `note` in `--json` (`portfolios`, `statusNotes`); `OBSERVED_REFS` takes `speaker`.
  - **`star/v1`** (RFC 0041), under the new `rfc0041` flag (`src/stars.ts`): `starProblems`, `starLineProblems`, `standingStars`; `show`'s `★ event 019cadd3… · <note>`; the Day's ★ after a disposition on every row it lists and its `stars`.
  - **`scene-review/v1`** (RFC 0040 §5), under the new `rfc0040` flag (`src/sceneReviews.ts`): `sceneReviewProblems`; `show`'s `scene 2:10–2:50 ≠ Hjem` and `superseded by #N`. `video/v1` and `attribution/v1` are not read.
  - **`keeper/v1`** (RFC 0024's amendment of 2026-10-14): `show` prints a keeper's `note`; a keeper another names in `supersedes` is no hero.
  - **The signed day's amendment 4** (a re-sign keeps the standing signature's confirmations) is the writer's; the readers already read it, and `tests/cross-impl.test.ts` has the reference re-sign a day four ways and both read each alike.
  - Not implemented: RFC 0030's amendment (no bundle here), RFC 0037's `idea_rows` (the reference's idea proposals), schema/resolution-v1-speaker.schema.json, RFC 0040's `video/v1` and `attribution/v1`, and the drafts RFC 0039 (anchor) and RFC 0042 (hold).
- RFC 0036, *Goals, reviews, drafts and chapters; the day's boundary; the freshness of a signature* (bighydro/logbook, draft of 2026-10-13, and its amendment 1, PR 269, open), read behind the `rfc0036` flag, off by default until the RFC is Final: `LOGBOOK_TS_FLAGS=rfc0036` (`src/flags.ts`; an unknown flag name is refused). Nothing here writes a goal, a review, a draft or a chapter, and with the flag off every reader prints what it printed before.
  - `goal/v1` and `review/v1` (`src/goals.ts`): `goalProblems` and `reviewProblems` hold a line to the RFC's field tables (tier 2 and `source` `manual`, MUST; the three horizons; the five dispositions, `let go` with its space; the five periods; `until` not before `from`); `reviewRecordProblems` to the writer's rules against the record (a goal line not retracted, `at` not on a day before the goal's `from`, nor more than five minutes after `recorded_at`; a backfilled `at` is a feature); `reviewKey`, the dedupe key `(goal, period, at)`; `standingGoals` and `standingGoal` (rewording supersedes; a retracted rewording leaves the earlier goal standing); `standingReviews`, the latest by `at`, then `seq`, a review counting for the goals that reword the one it names; `openGoals`.
  - `draft/v1` (`src/drafts.ts`): `draftProblems`, the five fields the reference's Day checks in its words and its order (`read_head`, `read_count`, `language` as a BCP 47 tag, `segments` with the segment rule, `{text, evidence}` or `{text, unsupported: true}` and no third shape, naming the first malformed segment as the reference does, and `supersedes`), and in this implementation's words `source` `model:<name>`, `unit`, `subject` in the unit's form (a real day, an ISO week, a month, a year, line ids, a person), amendment 1's `window` (MUST on a person, absent elsewhere) and `read_policy`; `readDraft`, the draft as the reference's Day reads it, each segment supported or not and why, a segment resting on a line not on the unit shown unsupported (`evidence names a line that is not on the day`), and the `malformed` list; `draftTierProblems`, a tier never below a line a segment cites; `draftKey`, `(source, unit, subject, read_head)` and the window for a person; `standingDrafts`.
  - `chapter/v1` (`src/chapters.ts`): `chapterProblems`; `chapterKey` `(name, from)`, a closing line that supersedes the open one not counted as a duplicate; `standingChapters`; `chapterOf`, the standing chapter open on a local day, the later by `from`, then `seq`, when two are, with the clash; `chapterClashes`.
  - `day_start` (`src/dayStart.ts`): `readDayStart` (absent or null is `00:00`); `localDayOf`, the rule, an instant whose wall clock is before `day_start` belongs to the day before, on the wall clock after localising, so the night the clocks change moves no line; `localToday`. Under the flag every reader that groups lines by day (`show`, `day`, `days`, `trips`, the rollups, `people`, `stats`, `sources --gaps`) refuses a value that is not a clock in the reference's sentence, `<command>: logbook.json has day_start '6am', which is not a clock from 00:00 to 23:59 written HH:MM; …`, exit 2, and a clock other than midnight as well, since none of them puts a line on a day by it yet; `verify`, `add` and the list of sources go on.
  - `signed_within_days` (`src/policy.ts`): read from a `policy/crossing.json` entry under the flag, a positive whole number of days, refused naming the file and the entry otherwise; `crossingEntry`; `dayGate` and `lineCrosses` compose it with `max_tier` (on the line) and `until` (on the entry, the header included) as the RFC says, a day crossing only when its standing signature was written on one of the local days from N before today through today, `--unsigned` lifting RFC 0034's default and never the entry's rule; `signedOn`.
  - `show` prints a `draft/v1` line (`draft of day 2026-06-13 · 5 lines read at bb97e90d · 4 segments, 1 unsupported · supersedes an earlier draft`) and a `chapter/v1` line (its name) as the reference does, under the flag.
  - Tests from the RFC's example lines (`tests/rfc0036-examples.ts`) and invalid variants of each; `tests/fixtures/rfc0036-sample`, a record of them with `expected-show/` captured from the reference; `tests/cross-impl.test.ts` holds both implementations to the same `show` rows, the same `day_start` sentences on nine bad values, and the same reading of a day's draft across eleven variants. The conformance samples are untouched and verify to the same heads. SPEC-QUESTIONS 86–90.

- `signed-day/v1` amendment 1, dispositions (RFC 0034, 2026-10-08), read: the payload's optional `dispositions` maps a confirmed line's id to `kept`, `missed`, `dropped` or `carried`. `signedDayProblems` validates it in the reference's words (an object; every key an id in `confirmed`; every value one of the four), and holds `page.lines` to at least the number of lines confirmed, as the reference's `signing.validate` does. `dispositionsOf` keeps the valid entries and never fails on the rest (SPEC §5); the Day carries the map under `signed.dispositions` and prints a tick, a cross, a dash or an arrow (`✓ ✗ – →`) before each disposed line, on the all-day, event, transcript, note, mail, call, keeper, flight and unplaced rows, as the reference's `day` does (`mark`); `show` lists the counts on the signature's row (`signed 2026-03-01: 2 lines confirmed of 2 · kept 1, missed 1 · <note>`, `countsText`). - `add` takes `--no-wait`: while another writer holds the record's lock it prints `add: another logbook command is writing to this record (<command>, since <time>); --no-wait, so not waiting` and exits 2, as the reference's global `--no-wait` does; without it, it waits. `addNote` takes the same as `wait: false`, a `command` the lock names its holder by (`logbook-ts add` by default), and `say`, where its one-line notices go; `takeWriterLock` and `withWriterLock` are exported for a future `append`, with `WriterBusy`, `HeadMoved` and `TailAhead`, each a `LogbookError` (`TailAhead` is not a `HeadMoved`: reading the head again does not mend it). `--no-wait` and `repair tail`'s flags go anywhere after the command.
- `repair tail <root> [--dry-run] [--no-wait]`, as the reference's `logbook repair tail` (its #294; decision B): when a crash between a line and `logbook.json` (SPEC §3, write order) left the files ending past it, it verifies the whole chain — streamed as `verify` streams it, one line per month file, the first twenty lines past the head kept to list — and only then sets `logbook.json` to the last line's `seq` and head through an fsynced temp file and a rename, keeping its other keys, under the writer lock (its holder `logbook-ts repair tail`, the dry run too). It prints what the reference prints: the lines past the head by `seq`, file, row and hash (twenty, then `… and N more lines`), what it would set (`--dry-run`, nothing written) or set, and `verify`'s verdict; `nothing to repair: …` on a record that verifies; exit 0. It refuses, changing nothing (`repair tail: …; nothing was changed`, exit 2): any fault in the files, before the head or past it, named as `verify` names it; the files ending before `logbook.json`; the files ending at its `seq` under another head; a first line past the head that does not chain from it; a `logbook.json` that names no seq and head. Under `--no-wait` a held lock is `repair: …; --no-wait, so not waiting`, exit 2. `repairTail`, `repairTailText`, `RepairRefused` and the `RepairTail`, `RepairTailOptions` and `TailLine` types in the library. Its words and exit codes are the reference's, read by running it; it leaves out the reference's index clauses, names its own program, and refuses a record wrong before the head where the reference sets `logbook.json` forward and then reports it invalid (SPEC-QUESTIONS 92).
- `readChain` (src/verify.ts) takes a probe, `{ at, tail, begin }`: the hash of the line at one seq (`Chain.headAt`, GENESIS for 0) and each line past it as the walk takes it, in seq order, with where it lies; `begin` marks the start of each walk, since a month file out of seq order sends the record to the sorted read, which begins again. Nothing is gathered for it.

- One writer at a time, and the write order of SPEC §3. `addNote` took no lock and did not flush the appended line before replacing `logbook.json`: two `add` processes that both validated the record and then appended wrote the same `seq` twice and left a chain that no longer verified, and a crash between the two writes could leave `logbook.json` naming a line the month file did not yet hold. Now the whole of an append holds `state/writer.lock` in the record folder, the file the reference's writers hold (`{"pid", "command", "since"}`, as it writes it): a holder whose process lives is waited for, with `another logbook command is writing to this record (<command>, since <time>); waiting` said once, or refused at once with `WriterBusy` when the caller does not wait, however old its `since`; a holder whose pid is gone, is not a positive whole number, or is this process's own and dated before it started (a crashed writer's pid given again), is taken over with `a stale lock from <command> (pid <pid>, since <time>) whose process is gone; taking it over`, a missing field printed `?`, null `None` and anything else as Python's `str()` — each as the reference prints it, read by running it. A lock naming this process's own pid dated since it started may be another thread's and is waited for; a second take in the thread that holds the lock is refused instead of waiting on itself. The lock is made in one step: the holder is written and fsynced to a temp file in `state/` and hard-linked to `writer.lock`; `link`, like the reference's exclusive create, fails when the name exists, so no reader finds this implementation's lock empty and the two implementations still exclude each other; a filesystem that cannot link gets the reference's own two steps. A lock that names no holder (empty, cut short, not a JSON object: the reference's own lock is all of these between its create and its write) is held to rule A, the reference's rule alone (the owner's decision of 16 October, which replaces that of 15 October and its mtime clause): it is a writer between its create and its write while it changes, and a leftover of a crash once the same file has named no holder for half a second, whatever its mtime, removed then without a word and taken, under `--no-wait` too, as the reference removes it; while it keeps changing the writer reads it again, says once `another logbook command is taking the lock on this record (state/writer.lock names no holder yet; if none is running, remove it); waiting`, and under `--no-wait` refuses with that sentence. The reference, run under `strace`, reads such a lock, sleeps half a second, reads it again and removes it, judging by its first read and not by mtime; here the same file must name no holder on every read for half a second, so a lock replaced or touched meanwhile starts the half second over, and an empty leftover dated ahead of the clock (another machine's, on a shared folder) is taken after the same half second (SPEC-QUESTIONS 91). Every takeover is a compare-and-remove under a second exclusive file, the lock read again on one handle (bytes, inode, size, mtime) right before the unlink, and `taking it over` is said once it is done; an empty reclaim file gets rule A too, and one naming a living pid is waited for with one line after half a second (`… (state/writer.lock.reclaim names pid N); waiting`), or refused under `--no-wait`, never waited out in silence. A writer that took the lock in the two steps and lost it under rule A, held between them past half a second, notices (the file it wrote has no links, or, once closed, the lock's name is another file, one naming another holder, or none: Windows before libuv 1.49, Node 20, keeps a removed file's name and one link while a handle holds it, and a freed inode number is soon given again) and waits on the writer that took it; on Windows under Node 20 the writer that removed it cannot read the lock again while the stalled one holds the name, delete-pending, and refuses after Windows' five seconds of retries with `cannot read the writer lock (EPERM …)`, nothing written. A `state/` or lock that is a link to nowhere is refused, not spun on; a lock that is a folder is refused as a lock that cannot be read; a second take in one thread is known whatever spelling of the record it names (the lock's real path). A release removes the lock only while it is still the writer's own, and never throws over the writer's own error; a two-step take whose write fails (a full disk) removes the empty lock it made.
